# lil-redis v2 plan

v1 shipped a working single-namespace Redis on a Durable Object: RESP2 over
WebSocket, SQLite storage, strings/hashes/lists/sets, TTLs. It is deployed
open at redis.yaqeen.me with no auth.

v2 goal: make it something you would actually point an app at. Ordered by
priority; each phase is independently shippable.

---

## Phase 0: Lock the door (auth)

The only blocking issue for real use.

**Design**
- Secret `AUTH_TOKENS` (comma-separated, or JSON map `{token: namespacePattern}`)
  set via `wrangler secret put`.
- RESP: connection starts unauthenticated. Only `AUTH`, `PING`, `QUIT`, `HELLO`
  are allowed until `AUTH <token>` succeeds (`-NOAUTH Authentication required.`).
  Track per-socket auth state with `ws.serializeAttachment()` so it survives
  hibernation.
- HTTP: `Authorization: Bearer <token>`. WebSocket upgrade: same header, or
  `?token=` query param for browser clients that cannot set headers.
- Token-to-namespace scoping: a token may be restricted to a glob of
  namespaces (`myapp:*`). Enforced in the Worker before the DO is touched, so
  unauthenticated traffic never wakes a DO (costs nothing).
- Rate limit failed AUTH attempts per IP using a tiny separate DO or the
  Workers Rate Limiting binding.

**Files**: `src/index.ts` (gate), `src/lil-redis.ts` (per-socket state),
new `src/auth.ts`.

## Phase 1: Protocol completeness

Make real Redis clients (`redis-cli`, ioredis, node-redis, redis-py) work.

1. **TCP is not available on Workers**, so a client needs a WS bridge.
   Ship `scripts/bridge.mjs`: listens on `localhost:6379`, forwards raw
   bytes to `wss://host/db/<ns>` one connection per TCP client. Then
   `redis-cli -p 6379` just works. This is the single highest-leverage
   DX feature.
2. **`HELLO` / RESP3 negotiation**: reply to `HELLO 3` with a map; keep RESP2
   encoding for now (clients fall back), but recognise the command so
   ioredis/redis-py do not fail on connect.
3. **Binary-safe values**: store `BLOB` instead of `TEXT`; parser hands out
   `Uint8Array` and only decodes to string for command names. Needed for
   anything that stores msgpack/protobuf.
4. **`SCAN` / `HSCAN` / `SSCAN`**: cursor = rowid offset. `KEYS *` on a big
   namespace is a footgun.
5. **`MULTI` / `EXEC` / `DISCARD` / `WATCH`**: queue commands per socket,
   run the batch in one `transactionSync`. Trivial given the current design,
   and it unlocks optimistic locking patterns.
6. **`OBJECT ENCODING`, `TOUCH`, `RANDOMKEY`, `COPY`, `DUMP`/`RESTORE`**:
   small, mostly for client compatibility and migration tooling.

## Phase 2: More data structures

Rough order of usefulness on a Durable Object:

1. **Sorted sets** (`ZADD ZRANGE ZRANGEBYSCORE ZREM ZSCORE ZRANK ZCARD
   ZINCRBY ZPOPMIN/MAX`). Table `zsets(key, member, score)` with an index
   on `(key, score, member)`. SQLite does range queries natively, so this
   is easier here than in real Redis. Leaderboards, rate limits, schedulers.
2. **Streams** (`XADD XRANGE XREAD XLEN XDEL XTRIM`, consumer groups later).
   The DO already has ordered durable storage and a WebSocket to push on;
   `XREAD BLOCK` becomes a natural fit with hibernation + alarms.
3. **Bitmaps / HyperLogLog**: `SETBIT GETBIT BITCOUNT`, `PFADD PFCOUNT`.
   Store as BLOB. Cheap to add once values are binary-safe.
4. **Geo**: skip unless asked for.

## Phase 3: Pub/Sub and blocking ops

Where a DO is genuinely better than Redis: the server already holds the
client sockets.

- `SUBSCRIBE` / `PSUBSCRIBE` / `PUBLISH` / `UNSUBSCRIBE`. Subscription set
  per socket stored via `serializeAttachment` so it survives hibernation.
  `PUBLISH` fans out with `ctx.getWebSockets()`; a tag per channel
  (`acceptWebSocket(ws, [channels])`) lets `getWebSockets(tag)` do the filter.
- Keyspace notifications (`__keyevent@0__:expired`) driven from the alarm
  sweep, essentially free.
- `BLPOP` / `BRPOP` / `BRPOPLPUSH` / `XREAD BLOCK`: park the request, store
  waiter list in memory (rebuild from attachments on wake), wake on push, use
  the alarm for timeouts. This is a real differentiator; doing it in
  Redis-on-a-VM requires the same server anyway.
- Pub/sub across namespaces is out of scope (each DO is its own island).

## Phase 4: Operability

- **`INFO` that tells the truth**: key count per type, SQLite file size
  (`ctx.storage.sql.databaseSize`), connected clients, uptime since last
  wake, alarm time.
- **`SLOWLOG`-ish**: log commands over N ms via `console.log` with
  structured fields; visible in Workers observability.
- **Storage limits**: a SQLite DO caps at 10 GB. Add `MAXMEMORY`-style
  configurable cap per namespace with `noeviction` (reject writes) and
  `volatile-ttl` (evict soonest-expiring) policies. Check
  `databaseSize` after writes.
- **Point-in-time recovery** exposure: `ctx.storage.getCurrentBookmark()` /
  `onNextSessionRestoreBookmark()`. Expose as `LIL.SNAPSHOT` /
  `LIL.RESTORE <bookmark>` admin commands. Free undo button.
- **Admin HTTP surface** under `/admin/*` (token-gated): list namespaces
  (needs a registry DO since DO namespaces are not enumerable), delete a
  namespace, export as RDB-ish JSON.
- **Metrics**: Workers Analytics Engine binding, one row per command
  (namespace, command, latency, bytes).

## Phase 5: Performance

Measure first. Likely wins, in order:

1. **Prepared-statement reuse**: `sql.exec` re-parses each call. Cache
   `SqlStorageStatement`s in the Store. Probably the biggest single win.
2. **Batch replies per message**: pipelined commands currently `ws.send()`
   once each. Concatenate all replies from one inbound frame into one send.
3. **Hash/set writes**: `hset` does a SELECT + UPSERT per field. Use
   `INSERT ... ON CONFLICT ... RETURNING` or compare `changes()` before/after
   to make it one statement.
4. **List `LRANGE` on large lists**: `LIMIT/OFFSET` is O(offset). Fine to a
   few thousand elements; beyond that, translate to `pos BETWEEN` using the
   known `lo`.
5. **Skip the alarm read on hot paths**: `getAlarm()` is awaited after every
   SET. Cache the scheduled alarm time in memory and only hit storage when
   the new expiry is earlier.
6. **Benchmark harness**: `scripts/bench.mjs` hitting the deployed instance
   with N concurrent WS clients, report p50/p99 per command class. Keep the
   numbers in the README.

## Phase 6: Client libraries

- `@lil-redis/client` for JS: thin wrapper over WebSocket + RESP with a
  typed command surface generated from `commands.ts`. Works in browsers,
  Node, and Workers (via `stub.exec` when co-located, WS otherwise).
- Adapter for BullMQ / ioredis-compatible surface is a stretch goal; the
  bridge from Phase 1 covers most of it.

---

## Explicitly not planned

- Multi-namespace atomicity, cross-DO transactions, or Redis Cluster
  semantics. One namespace = one DO is the whole point.
- Replication or `WAIT`: the DO storage layer already replicates.
- Lua scripting (`EVAL`). Sandboxing user code inside a DO is a project by
  itself; `MULTI/EXEC` plus `WATCH` covers most real uses.
- `SELECT <db>` with real separate databases. Use namespaces.

## Suggested order to ship

| Step | Effort | Why first |
|---|---|---|
| Phase 0 auth | small | unblocks everything else being public |
| TCP bridge + HELLO | small | redis-cli works; instantly credible |
| Sorted sets | medium | most requested missing structure |
| MULTI/EXEC, SCAN, binary-safe | medium | client compatibility |
| Pub/Sub + blocking pops | medium | the DO-native showcase feature |
| Prepared statements + batched replies | small | measurable speedup |
| INFO / limits / PITR admin | medium | needed before anyone trusts it |
| Streams | large | only if a concrete use appears |
